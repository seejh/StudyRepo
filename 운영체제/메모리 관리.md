# 메모리 관리
## 논리 메모리, 물리 메모리

* Logical address (=Virtual address)
  * 프로세스마다 독립적으로 가지는 주소 공간으로 각 프로세스마다 0번지부터 시작
  * cpu가 보는 주소는 logical address
* Physical address
  * 실제 메모리 주소

### 주소 바인딩
```
symbolic address -> logical address -> physical address

// symbolic address: 프로그래밍할 때 사람이 이해하기 쉬운 기호로 메모리 주소를 가리키는 거
```
cpu와 프로세스가 사용하는 주소는 가상의 논리 주소이고 이는 실제 메모리 주소에 매핑되어야 한다.
가상 주소가 실제 메모리에 바인딩(매핑)되는 시점이 언제인가<br/>
<img width="841" height="584" alt="image" src="https://github.com/user-attachments/assets/dac64bba-c076-4940-8eb8-4e19e04ef0d5" /><br/>
* 컴파일(Compile) 타임 바인딩
  * 컴파일할 때 물리 주소가 결정, 고정되며 변경하고 싶으면 재컴파일 필요.
  * 요새는 사용하지 않는 방식
* 로드(Load) 타임 바인딩
  * 프로그램 실행 중에 주소가 결정된다.
* 런(Run, Execute) 타임 바인딩
  * 로드 타임은 결정된 주소가 고정이라면 런타임 바인딩은 실행 중에 변경될 수 있다.
  * 그래서 매번 주소를 읽을 때마다 확인이 필요하며(변환) 이것을 cpu에서 하드웨어(mmu)가 해준다.

컴파일 타임의 경우 컴파일하여 나온 주소 0~40이 결국 물리 주소가 된다. 로드 타임의 경우 컴파일하면 논리 주소가 0~40으로 결정이 되고
그 후에 프로그램을 실행하면 물리 주소가 500~으로 결정된다. 런 타임의 경우 컴파일해서 논리 주소 0~40, 실행했을 때 300~으로 결정됬으나
이후에 700으로 물리 주소가 변경된 모습이다.

### MMU (Memory Management Unit)
<img width="789" height="558" alt="image" src="https://github.com/user-attachments/assets/2b27c120-b0d9-4363-8bac-4a558af09066" /><br/>
cpu가 프로세스의 명령어를 불러와서 처리할 때 접근하는 모든 주소는 논리 주소이며 실제 물리 주소는 알지 못한다. 이를 변환해주는 것이 MMU로, MMU는 
논리 주소를 물리 주소로 변환해주는 하드웨어 디바이스(소프트웨어가 아닌)이다.<br/>

위 그림에서 프로세스 p1은 논리 주소 0~3000, 물리 주소 14000~17000을 할당 받은 상태이다. cpu가 논리 주소 346에 액세스하려고 하고 MMU에서
논리 주소를 변환하여 실제 물리 주소 14346에 액세스한다. 여기서 알아야 할 것이<br/>

* relocation register (=base register)에는 실제 "물리 주소의 시작 주소"가 저장된다.
* 프로세스는 논리 주소 0부터 시작하며 물리 주소를 찾을 때 오프셋이라고 생각하면 된다.
 
논리 주소 346 => 실제 물리 주소 시작점(base register 값 == 14000) + 논리 주소(= 오프셋) => 14346 <br/>

<img width="672" height="334" alt="image" src="https://github.com/user-attachments/assets/70f2cf56-e3cd-4f3a-9596-5b3cdbbba493" /><br/>
limit register의 값은 논리 주소 범위로, 해당 프로세스가 할당 받은 메모리양이다. 이 값은 할당 받은 범위를 넘어서 접근하려고 하지는 않는지 체크하기 위한 것으로
MMU에서는 실제로는 아래와 같이 동작한다.

* cpu에서 논리 주소 접근
* MMU에서 limit register로 프로세스 할당 범위를 넘는지 체크
  * 만약 여기서 할당 범위를 넘으면 trap을 건다.
* 넘지 않았으면 base register 값을 더하여 (논리 주소 + base register = 접근할 실제 메모리) 변환

## 몇가지 용어 미리 설명
### Dynamic Loading
프로세스 전체를 미리 메모리에 다 올리는 것이 아니라 해당 루틴이 필요할 때마다 메모리에 load 하는 것.
프로그램에서 자주 사용되는 부분이 있고 자주 사용되지 않는 부분이 있는데 자주 사용되지 않는 부분을 메모리에 올리고 있으면 손해이다.
가끔씩 사용되는 많은 양의 코드인 경우에 유용하다.(예: 에러 처리 루틴) 운영체제의 지원없이 프로그램 자체에서 구현 가능하다. (OS가 라이브러리로 지원하면
개발자가 구현)

### Dynamic Linking
링킹은 우리가 짠 소스코드 목적 파일들을 하나로 엮어서 실행 파일로 만드는 것.

* static linking
  * 라이브러리가 프로그램의 실행 파일 코드에 포함
* dynamic linking
  * 라이브러리는 외부에 따로 존재하고 실행 파일에는 라이브러리를 찾는 코드만 존재
  * 라이브러리 호출 부분에 라이브러리 루틴의 위치를 찾기 위한 포인터를 두고
    * 라이브러리가 이미 메모리에 올라와 있으면 그 루틴의 주소로 간다.
    * 라이브러리가 올라와 있지 않으면 디스크에서 읽어온다.

운영체제의 도움이 필요하다.

### Overlays
위의 Dynamic Loading과 같다. 다만 Dynamic Loading은 OS에서 지원하는 기능을 쓰는 것이고 여기서는 개발자가 직접 구현하는 것이며
메모리양이 부족했던 옛날에 사용하던 방식이라고 한다.

### Swapping
<img width="630" height="482" alt="image" src="https://github.com/user-attachments/assets/ec5a4414-cde2-471a-bed4-760997304217" /><br/>
프로세스를 메모리에서 디스크(backing store)로 내보내고 들이고 하는 것. 중기 스케줄러(swapper)에 의해 우선도가 낮은 프로세스를 swap out하고
우선도가 높은 프로세스를 swap in한다.<br/>

* 주소 바인딩 고려
  * 컴파일 타임, 로드 타임 바인딩의 경우 swap in 될 때 원래 메모리 위치로 가야 한다.
  * 런타임의 경우 빈 곳으로 아무데나 갈 수 있다.

swap time은 transfer time(swap 되는 양에 비례)이 대부분이다.
메모리에서 프로세스 전체가 swap out/in 되는 것은 파일 입출력과는 다르게 양이 굉장히 많다.
디스크 접근 시간의 경우 seek time이라고 해서 디스크 헤드가 이동하는 시간이 거의 대부분을 차지하고 실제로 데이터를
전송하는 transfer time은 미미한 시간을 차지한다.

## Allocation of Physical Memory, 물리 메모리 할당
메모리는 일반적으로 두 영역으로 나누어 사용한다.
* OS 상주 영역
  * 낮은 주소 영역, 앞 부분에 상주
* 사용자 프로세스 영역
  * 높은 주소 영역

### 사용자 프로세스 영역 할당 방법
* Contiguous allocation, 연속 할당
  * 고정 분할 방식, Fixed Partition Allocation
  * 가변 분할 방식, Variable Partition Allocation
* Noncontiguous allocation, 비연속 할당
  * Paging
  * Segmentation
  * Paged Segmentation

### 연속 할당, Contiguous Allocation
<img width="753" height="351" alt="image" src="https://github.com/user-attachments/assets/4d9a22a0-6e5e-4453-9fcd-0ca1aecf71ad" /><br/>
프로세스를 메모리에 하나의 덩어리로 통째로 올리는 것으로 고정 분할, 가변 분할 방식이 존재한다.

#### 연속 할당 - 고정 분할 방식, Fixed Partition Allocation
물리적 메모리를 몇 개의 분할로 나누고(각 분할의 크기는 다를 수 있다) 각 분할에 하나의 프로그램을 적재하는 방식.
그러니까 프로그램이 올라가기 전에 공간을 미리 정해진 크기로 나누는 방식으로 융통성이 없어 아래와 같은 문제가 있다.

* 동시에 load 되는 프로그램 수가 고정된다.(분할 개수)
* 수행할 수 있는 프로세스의 최대 크기가 제한된다.
* 외부 조각, 내부 조각 발생

<br/>

* 내부 조각, 외부 조각 (Internal/External Fragmentation)
  * 위 그림, 고정 분할 방식에서, 프로그램 a가 분할 1에 로드, 이후 프로그램 b가 들어오는데 분할2 보다 크기에 상주할 수 없고 분할3에 로드.
  * 이러한 상황에서...
  * 내부 조각 (Internal Fragmentation)
    * 분할3을 내부 조각이라고 한다.
    * "프로세스 크기 < 분할의 공간"으로 공간 내부에 낭비되는 메모리 공간
  * 외부 조각 (External Fragmentation)
    * 분할1을 외부 조각이라고 한다.
    * 프로그램이 배정 받지 못한 공간, 프로그램의 크기 보다 작아서 활용하지 못하는 공간.
  * 다만 이 용어들이 엄격하게 사용되지는 않는다고 한다. 외부 조각의 경우 나중에 그 공간에 딱 맞는 프로세스가 실행되면 사용할 수 있고 그때 그때 조각에 대한 해석이 달라질 수 있다.

#### 연속 할당 - 가변 분할 방식, Variable Partition Allocation
프로그램을 할당할 때 그 크기에 맞춰서 할당한다. 따라서 여기서는 내부 조각 문제는 발생하지 않고 분할의 크기와 개수가 고정되지 않는다.

* Hole (=외부 조각)
  * 위에도 설명했듯이 애매해서 그냥 빈 공간들이 생기는 것을 hole이라고 한다.
  * 가변 분할 방식을 쓰다 보면 hole 들이 생기는데 이후에 실행하는 프로그램을 어느 홀에 로드시킬 것인지를 결정할 필요가 있다.
  * 가변 분할 방식에서 size n의 요청을 만족하는 hole을 찾는 방법
    * first-fit
      * size n 이상인 것 중 최초로 찾는 hole에 할당
      * 리스트를 다 돌 필요가 없다 -> 탐색 속도 이점
    * best-fit
      * 모든 hole 리스트를 탐색 후 프로그램 크기에 가장 맞는 (size n 이상인 것들 중 가장 작은) hole에 할당
      * 공간 이용률에 이점
    * worst-fit
      * 모든 hole 리스트를 탐색 후 가장 큰 hole에 할당
   * first-fit과 best-fit이 worst-fit 보다 속도와 공간 이용률 측면에서 효과적이라고 한다.

* compaction
  * 위의 방식들을 사용해도 hole은 생긴다. compaction은 사용중인 프로세스 메모리 공간을 한 군데로 몰고 다른 쪽으로 hole들을 몰아서 큰 block을 만드는 방법으로 실행중인 프로세스들을 옮기기에 매우 비용이 많이 드는 방법이다. 심지어 프로세스가 런타임 바인딩 방식이어서 동적 재배치가 가능해야만 수행할 수 있다.

 
### 비연속 할당, Noncontiguous allocation
* 현재 OS에서 사용하는 방법 (고정 할당 사용하지 않는다)
* 하나의 프로세스가 메모리에 분산되어 올라갈 수 있다.
* Paging, Segmentation, Paged Segmentation이 있다.

#### 비연속 할당 - Paging, 페이징
<img width="475" height="432" alt="image" src="https://github.com/user-attachments/assets/6e7d31a2-4867-4733-9f10-70a89d583629" /><br/>
연속 할당의 고정 분할 방식과 비슷한 방법. 논리 주소 공간을 페이지라고 하는 작은 단위(일반적으로 4KB)로 나누어 필요한 만큼 할당하는 방법.
논리 메모리 공간을 페이지라는 작은 단위로 나누고 그 논리 메모리 공간을 실제로 담당하고 있는 물리 메모리 공간은 프레임이라고 한다.

* 페이지: 논리 메모리 공간을 일정 크기로 자른 블록, 보통 4KB 공간
* 프레임: 물리 메모리 공간을 페이지와 동일한 크기로 자른 블록
* 페이지 테이블:
  * 논리 주소의 어느 페이지가 물리 주소의 어느 프레임에 위치하는지 매핑 기록 테이블
  * 이러한 페이지 테이블은 메인 메모리에 상주한다. 이로 인해 모든 메모리 접근 연산에는 2번의 메모리 액세스가 필요하게 된다.
    * 주소 변환을 위한 메모리 테이블 접근 1번
    * 그 후 실제 데이터의 메모리에 접근 1번
  * mmu에서 기존에 사용하던 두 개의 레지스터(base, limit)를 다르게 사용한다.
    * ptbr, page table base register = 메모리 상에서 페이지 테이블이 어디에 있는지 포인터
    * ptlr, page table length register = 페이지 테이블 크기

32비트 시스템은 메모리 주소 표현에 32 비트를 사용하고 이는 2의 32승 = 4GB 개의 주소를 사용할 수 있다.<br/>
여기서 페이지의 크기가 4KB이면, 페이지의 개수는 1M 개 있게 된다.<br/>
페이지 테이블 엔트리의 크기가 4B이면, 4MB의 공간이 페이지 테이블로 낭비가 된다.<br/>

* 페이지 테이블 엔트리: 페이지 테이블에서 페이지와 프레임 매핑 정보를 나타내는 각 행으로 페이지 개수만큼 있다.
* 페이지는 1M개 있고 페이지 테이블에는 페이지에 대한 정보가 1M개 * 각 4B = 4MB
* 페이지 테이블은 메모리 저장된다.

심지어 사용자 프로세스가 해당 공간을 다 쓸 수 있는 것도 아니기에 낭비는 더 심해진다.<br/>

### Multilevel Paging, 다단계 페이징 

이러한 공간 낭비를 줄이기 위해 Multilevel paging 이라는 방법이 있다고 한다. 일반적으로 이런 방법들은 공간 사용률을 줄이려고 연산을 더 많이 하는 방법을
선택한다. 메커니즘을 겉핥으면 아래와 같은 모습이다.

* 2단계 페이징의 경우, 주소 변환을 위해 메모리에 2번 접근 + 실제 데이터 접근 1번 => 총 3번의 메모리 접근
* 4단계 페이징의 경우, 주소 변환을 위해 메모리에 4번 접근 + 실제 데이터 접근 1번 => 총 5번의 메모리 접근

이렇게 단계를 높이면 공간을 많이 줄일 수 있지만 메모리 접근 시간이 늘어난다. 

TLB 캐시

주소 공간이 커지면 공간 낭비가 커지기 때문에 다단계 페이징 테이블이 필요하다. 공간을 줄이는 만큼 탐색 오버헤드가 늘어나는데 이를 TLB를 사용해서 
메모리 접근 시간을 줄인다. 
```
4단계 페이지 테이블을 사용하는 경우에서 메모리 접근 시간 100ns, TLB 접근 시간 20ns, TLB hit ratio 98%.

effective memory access time = 0.98 * (100 + 20) + 0.02 * (500 + 20) = 128ns.
결과적으로 주소변환을 위해 28ns만 소요.
재수가 없어서(2%) 오래 걸릴 수도 있지만 대부분(98%) 28s.
```
