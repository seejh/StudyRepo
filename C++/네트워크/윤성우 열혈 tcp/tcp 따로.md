## TCP 상태
* LISTEN: 서버가 연결을 기다리는 중
* SYN_SENT, SYN_RECV: 핸드 쉐이크 진행 중
* ESTABLISHED: 연결되어 송수신 중
* FIN_WAIT / LAST_ACK: 종료 절차 진행 중
* TIME_WAIT: 먼저 닫은 쪽, 잔여 패킷 대비로 대기
* CLOSE_WAIT: 상대가 닫았는데 내 압이 아직 close() 안한 상태
실무 핵심: TIME_WAIT은 연결을 먼저 끊은 쪽에서 들어가는 정상적인 상태로, 짧은 연결을 많이 맺을수록 쌓인다.
보통 문제될 것이 없으며 반면 CLOSE_WAIT은 내가 passive일 때 들어가는 상태로 이게 많으면 거의 항상 내 애플리케이션이 소켓을
close()하지 않는 '버그'이다. 

## 4Way Handshake
<img width="545" height="472" alt="image" src="https://github.com/user-attachments/assets/4295f933-b641-4c83-8b92-7aaf2d6279ee" /><br/>
a(active closer), p(passive closer)<br/>
a: established -> FIN_WAIT1 -> FIN_WAIT2 -> TIME_WAIT -> CLOSED<br/>
p: established -> CLOSE_WAIT -> LAST_ACK -> CLOSED<br/>

### 정상 흐름
__1.a는 FIN을 보내고 상대의 ACK를 기다린다. 상태가 FIN_WAIT_1로 변경된다.__ <br/>
2.p는 FIN을 받고 상대에게 ACK를 보낸다. 상태가 CLOSE_WAIT으로 변경된다. <br/>
__3.a는 ACK를 받고 상대의 FIN을 기다린다. 상태가 FIN_WAIT_2로 변경된다.__ <br/>
4.p는 FIN을 보내고 상대의 ACK를 기다린다. 상태가 LAST_ACK로 변경된다. <br/>
__5.a는 FIN을 받고 상대에게 ACK를 보낸다. 상태가 TIME_WAIT이 된다.__ <br/>
6.p는 ACK를 받고 CLOSED가 된다. <br/>
__7.a는 시간이 지나면 CLOSED가 된다.__ <br/>

### 각 구간별 생길 수 있는 문제
a가 FIN을 보내고 상대의 ACK를 못 받는 경우(1):<br/>
a가 FIN을 보냈는데 상대가 그에 대한 ACK가 없는 경우, 현재 a는 FIN을 보내고 FIN_WAIT_1인 상태이며 이 경우 a는 본인이 보낸
FIN 패킷이 유실되었다고 생각하여 FIN 패킷을 일정 주기로 재전송하다가 timeout을 넘으면 연결을 끊는다.<br/>

a가 FIN을 보내고 상대의 ACK는 받았으나 FIN을 못 받는 경우(3):<br/>
(active 입장) a가 FIN을 보내고 상대의 ACK까지는 받고 현재 FIN_WAIT_2로 넘어가 상대의 FIN을 기다리는 상태.
timeout 시간까지는 대기하다가 연결을 끊는다.<br/>

(passive 입장) a가 상대의 FIN을 받고 ACK 응답 후 CLOSE_WAIT 상태 진입한 상태. 이게 프로그래머 입장에서는 "현재 애플리케이션에서 recv()를 걸어두고
대기 중 -> FIN 패킷 수신 (0 BYTE RECV) -> close() 호출" <- 이렇게 하는 것이 정상적 흐름이고 여기서 FIN 패킷 수신 후 close() 호출을 해야 상대방에서 FIN 패킷을
전송한다. 그렇지 않아도 커널에서 timeout을 둬서 자동으로 보내주기는 하지만 상대방 입장에서 기다려야 하고 나 또한 CLOSE_WAIT으로 오래 기다려야 한다.<br/>
쉽게 말하면 CLOSE_WAIT 상태는 애플리케이션 레벨에서 종료할 준비를 주는 단계이며 애플리케이션에서 close()를 명시해주면 상대에게 FIN을 보낸다. close()를 명시하지 않더라도
OS 레벨에서 타임아웃으로 자동으로 보내주고 프로세스가 정상, 강제, 크래시가 나서 종료되는 경우라 할지라도 OS 레벨에서 상대에게 FIN 패킷을 보내준다.
프로세스가 종료되는 시점에 소켓 커널 버퍼에 상대로부터 받았지만 아직 애플리케이션이 읽지 않은 데이터가 남아 있으면 커널은 정상적 종료가 불가능하다 판단하여 FIN 대신
RST 패킷을 보내 연결을 즉시 끊을 수도 있다.

## TCP Keep Alive
TCP 연결은 신뢰할 수 있도록 설계되었지만 거기에도 맹점이 있다. 예를 들어 상대방이 FIN, RST 패킷을 보낼 수도 없게 종료될 때(전원 끊김, 케이블 끊김 등), 이쪽에서는
이를 인지 못하고 연결을 유지하게 된다. 이 상태로 파일 디스크립터, 메모리, 연결 풀을 낭비하게 된다.<br/>

TCP의 신뢰성 메커니즘은 ***확인 응답(ACK)*** 이다. 타임 아웃을 활용하여 상대방의 ACK를 받음으로써 신뢰성이 지켜지는 것으로 이는 ***데이터를 전송할 때만*** 동작한다.
데이터를 보내지 않고 ***유휴 상태인 경우 확인할 수 없다.*** <br/>

이를 해결하기 위해 ***Keep-Alive*** 를 사용한다. 애플리케이션에서 데이터가 흐르지 않을 때(유휴 상태) 운영체제에서 원격지로 작은 프로브 패킷을 던지고
원격지에서 응답을 하면 살아 있는 것, 응답이 없으면 연결이 끊긴 것으로 간주하여 연결을 끊는 방식으로 구체적으로는 아래와 같이 동작한다. <br/>

### Keep-Alive 옵션
* Keep-Alive Time: 첫 번째 프로브가 나가는 타이머 (기본 7200초, 2시간)
* Keep-Alive Interval: 첫 번째 이후 프로브 간격 (기본 75초)
* Keep-Alive Probes: 연결 종료를 선언하기 위한 총 프로브 횟수 (기본 9번)

***(리눅스 기준)*** 애플리케이션의 마지막 데이터 송수신 후 타이머를 돌리고 시간이 다 될 동안 활동이 없으면 운영체제는 프로브 패킷을 전송한다(Keep-Alive Time).
이에 상대방이 응답하면 타이머 리셋, 응답이 없으면 다음 프로브 패킷이 전송된다(Keep-Alive Interval). 이 후로 몇 번 더 실패하면 해당 연결은 
끊긴 것으로 간주하고 끊는다(Keep-Alive Probes). <br/>

Keep-Alive 옵션을 사용하려면 ***소켓에서 Keep-Alive를 활성화하고 위의 세 변수를 조정하여 사용한다.*** 리눅스에서 기본값으로 잡혀 있는 수치가 너무
보수적이기에 사용하려면 ***위의 옵션값에서 수치를 조정해서 사용해야 한다.*** <br/>

부연 설명으로, 프로브 패킷은 일종의 트릭으로, 의도적으로 잘못된 시퀀스 번호를 전송하여 상대방의 수정 응답을 유도하는 것으로 이 패킷을 보내서
상대방에게 "나는 x번째 바이트를 기다리고 있어"라는 응답을 강요하는 것.<br/>

***Keep-Alive도 한계점***이 존재한다. Keep-Alive는 애플리케이션간에 대화가 없을 때 운영체제간에 tcp로 확인하는 것으로, ***커널 레벨의 확인***이라는 것.
예를 들어 애플리케이션이 교착 상태에 빠져 동작할 수 없는 상태에서도 운영체제에 의해 TCP 프로브 패킷에 응답할 수 있다. ***애플리케이션 수준의 장애를 감지하려면
애플리케이션 수준의 허트비트가 필요하다.*** <br/>

프로브 패킷은 페이로드없이 헤더만 있기는 하지만 이 또한 대역폭을 소비한다. 현대 네트워크에서는 거의 문제가 되지 않지만 제한된 환경에서는 고려할 가치가 있다고 하며
모바일 장치에서 잦은 프로브 패킷은 네트워크 인터페이스가 절전 모드로 들어가는 것을 막는다고 하며 모바일 애플리케이션은 keep-alive를 사용하지 않거나 빈도를 크게 줄인다고 한다.

## 네이글 알고리즘, TCP_NODELAY
TCP로 데이터를 송수신할 때 무조건 오버헤드가 따른다. ip 헤더(20)+tcp 헤더(20)+이더넷 프레임(18)+보내고자 하는 데이터(a). 
애플리케이션이 단 1바이트를 전송하면 그 1바이트는 59바이트 패킷에 담겨 이동한다.
```
오버헤드:  핵심 목적을 달성하기 위해 부가적으로 들어가는 비용
```
총 59바이트 전송에서 핵심 목적 1바이트, 그를 위해 추가되는 바이트(오버헤드)가 58바이트로 이를 비율로 나타내면 58/59 => 대략 98%가 오버헤드다.<br/>
이렇게 tcp는 데이터를 전송할 때 무조건 오버헤드가 있으며, 보내고자 하는 데이터의 크기가 작을수록 오버헤드가 늘어나기에,
네이글 알고리즘은 이 오버헤드를 최대한 줄이기 위해 패킷을 모아서 보내는 것.<br/>

네이글 알고리즘 설정은 소켓에서 TCP_NODELAY 옵션으로 설정하는데, 활성화하면 네이글 알고리즘을 사용하지 않겠다는 것으로, 패킷은 더 많아지고 오버헤드도 늘어나지만
즉각적인 전달이 보장된다.<br/>

### 네이글 알고리즘 규칙
* 전송할 데이터가 MSS(최대 세그먼트 크기, Maximum Segment Size) 이상이라면 즉시 전송.
* 전송할 데이터가 MSS 미만인데 이전에 보낸 데이터가 없으면(ACK를 못 받은 게 없으면) 즉시 전송.
* 전송할 데이터가 MSS 미만인데 이전에 보낸 데이터가 있으면(ACK를 못 받은 게 있으면) 꽉 찰 때까지 대기.
첫 번째 전송은 즉시 전송, 그 후의 전송들은 MSS를 채우면 즉시 전송, 그렇지 않으면 기존에 보낸 패킷들에 대한 ACK를 받을 때까지 대기.<br/>

이 방식은 네트워크 상황에 맞게 스스로 조절된다. ACK가 빠른 네트워크에서는 버퍼링이 최소화된다.
ACK가 지연되는 느린 네트워크에서는 더 적극적인 일괄 처리가 일어난다. 

### 사용 사례
실시간 게임의 경우 플레이어의 입력은 서버에 바로 도달해야 한다.

실시간 게임이 전형적인 사례이다. 플레이어의 입력은 서버에 바로 도달해야 한다. 왕복 지연을 기다릴 여유가 없다. 플레이어는 30~50ms 이상의
지연을 체감한다. 다음 입력을 보내기 전에 ACK를 기다리면 게임이 느리고 반응 없는 것처럼 느껴진다.<br/>

원격 데스크톱 프로토콜은 마우스 위치를 즉시 업데이트해야 한다. 일괄 처리 지연이 발생하면 커서가 사용자의 손 움직임보다
뒤쳐지게 되고 이 괴리감이 사용자를 불편하게 한다.<br/>

대용량 데이터 전송(파일 다운로드, 백업, 동기화)은 네이글 알고리즘을 유지해야 한다. 메가바이트 단위로 데이터를 이동할 때는
꽉 찬 패킷이 중요하고 지연은 문제가 되지 않는다.

### 지연된 ACK 문제 (delayed ACK) - 이부분 정리 필요
tcp의 효율 설정인 delayed ack와 상성이 좋지 않다.
<br/>
수신측은 모든 패킷에 즉시 ACK를 보내지 않는다. 발신 데이터에 ACK를 편승시키거나 여러 패킷을 한꺼번에 확인
응답하기를 기대하며 최대 200ms까지 기다린다.

### 모두가 TCP_NODELAY를 사용하면 네트워크 혼잡이 생기지 않나?
TCP의 혼잡 제어는 네이글 알고리즘과 별개로 동작한다. ***TCP_NODELAY가 활성화되어 있어도***
TCP는 패킷 손실과 네트워크 피드백에 따라 전송 속도를 조절한다. ***혼잡이 감지되면 속도를 줄인다.***

### 일부는 좀 기다렸다가 보낼 수 없나?
TCP NODELAY 설정했다고 패킷을 쏠 때마다 보내는 게 아니라 어떤 건 좀 모았다가 보내게 할 수 없나? 애플리케이션 계층에서 직접 처리해야 한다.

### UDP에서는?
UDP는 확인 응답이나 연결 상태의 개념이 없으므로 네이글 알고리즘이 적용되지 않는다. UDP의 모든 전송은 즉시 패킷이 된다.
UDP 애플리케이션에서 일괄 처리가 필요하다면 직접 구현해야 한다.

### 결론, 정리
네이글 알고리즘은 지연과 네트워크 대역폭 사이에서 트레이드 오프를 결정하는 것으로 지연에 민감하다면 TCP_NODELAY를 활성화해야 한다.
TCP_NODELAY의 활성화, 비활성화의 동작 방식이 너무 극단적이라고 생각된다면 TCP_NODELAY를 활성화한 후 애플리케이션 레벨에서
조절하는 것을 직접 구현해야 한다.

TCP 연결을 닫았다. netstat으로 확인한다. 연결은 여전히 그대로 남아 있고 TIME_WAIT으로 표시되어 있다. 
이는 버그가 아니다. TCP 연결을 닫은 후에도 네트워크 어딘가에 아직 전달되지 않은 패킷이 남아 있을 수 있기에 TCP는 연결을 닫은 후
60초 동안 대기하는 것이다.

TCP 연결이 닫힐 때 종료를 먼저 요청한 쪽은 4way-handshake를 완료한 후 TIME_WAIT 상태로 진입한다.

### TIME_WAIT이란?
TCP 연결이 닫힐 때, 종료를 먼저 요청한 쪽은 4way handshake를 완료한 후 TIME_WAIT 상태로 진입한다.
소켓은 커널의 연결 테이블에 그대로 남아, 로컬 주소와 포트, 원격 주소와 포트의 정확한 조합이 즉시 재사용되지 않도록 막는다.<br/>

지속 시간은 2MSL(Maximum Segment Lifetime, 최대 세그먼트 수명)로 최대 세그먼트 수명의 두 배이다. MSL은 TCP 세그먼트가 네트워크에서 
폐기되기 전까지 살아남을 수 있는 이론적 최대 시간으로 디폴트 값은 30초이다. 그래서 대부분 시스템에서 TIME_WAIT은 60초 동안 유지되지만
30초나 120초를 쓰는 시스템도 있다.

TIME_WAIT 동안 소켓은 버퍼도 없고 애플리케이션 상태도 없이 단지 커널 연결 테이블에서 한 항목을 차지하며 특정 조합의 재사용을 막는다.

### TIME_WAIT 존재 이유, TCP가 TIME_WAIT을 둬서 잊지 않는 이유
2가지 이유가 있다. 손실된 ACK 문제, 떠도는 패킷 문제.

손실된 ACK 문제<br/>
<img width="528" height="369" alt="image" src="https://github.com/user-attachments/assets/445ef49e-7d16-4e36-b69f-7f74903445a5" /><br/>
active closer가 FIN을 보내고 pc(passive closer)로부터 FIN, ACK를 받은 후 마지막으로 pc에게 ACK를 보낼 때 이 ACK가 유실된다면
pc는 LAST_ACK 상태를 유지하게 되고 이후 새 연결을 열어도 RST 응답만 하게 된다.

TCP 연결 종료는 ACK로 마무리된다. 그 마지막 ACK가 유실되면 상대방은 FIN을 재전송한다.
TIME_WAIT이 없으면 이미 연결 상태를 삭제한 시스템은 재전송된 FIN에 RST로 응답하게 된다.
그러면 상대는 연결이 실제로 닫혔는지 알 수 없다.

떠도는 패킷 문제<br/>
<img width="521" height="531" alt="image" src="https://github.com/user-attachments/assets/c7533a66-6781-47f1-b14e-4591c75a35a7" /><br/>
이전 연결에서 발생한 패킷이 새 연결을 맺은 후에 도착하여 새 연결에서 유효한 데이터로 받아 들여질 수 있다. 물론 패킷 번호까지 같아야 하기에
그 확률은 낮지만 TIME_WAIT은 이런 떠도는 패킷들이 모두 만료될 때까지 해당 주소, 포트 조합을 재사용하지 않음으로써 이를 방지한다.
2MSL이면 이전 연결의 모든 패킷이 사라졌음이 보장된다.

### TIME_WAIT이 문제가 되는 경우
TIME_WAIT은 정상적인 현상이다. netstat으로 확인했을 때 수천 개의 TIME_WAIT 소켓을 보더라도 그건 문제가 있는 게 아니라
시스템이 연결을 활발히 열고 닫았다는 뜻이다. 문제는 많은 연결과 해제가 생겨서 포트가 부족해질 때 생긴다. TIME_WAIT 소켓 하나는
임시 포트 하나를 차지한다. 대부분의 시스템은 약 28,000개 임시 포트를 제공한다(32768~60999). 60초 안에 같은 목적지로 28000개의
연결을 만들면 포트 공간이 바닥난다. 새 연결은 "요청한 주소를 할당할 수 없습니다" 오류와 함께 실패한다.

발생하기 쉬운 환경:
단일 api 엔드포인트로 http 클라이언트가 몰릴 때
대용량 트래픽을 전달하는 로드 밸런서
프록시 서버
연결 풀링이 제대로 구현되지 않은 어플리케이션

TIME_WAIT은 정확한 "원격 주소, 원격 포트, 로컬 주소, 로컬 포트" 조합의 재사용만 막는다.
다른 목적지로의 연결은 충돌하지 않는다. 수백 개의 서로 다른 서버와 통신하는 클라는 포트가 바닥날 일이 거의 없다.
하지만 하나의 서버에 초당 수천 건의 요청을 보내는 클라이언트라면 얘기가 다르다.

### TIME_WAIT 설정
net.ipv4.tcp_tw_reuse (리눅스)
커널 파라미터를 설정하면 TCP 타임스탬프가 새 연결임을 확인해줄 때 TIME_WAIT 소켓을 새 아웃바운드 연결에 재사용할 수  있다.
타임스탬프 덕에 오래된 패킷이 수락되지 않으며 클라이언트의 포트 소진 문제를 해결해주는 안전한 방법이다.

SO_REUSEADDR
이 소켓 옵션을 사용하면 서버가 이전 인스턴스에서 TIME_WAIT 상태인 소켓이 있는 포트에 바인딩할 수 있다.
60초를 기다리지 않고 서버를 재시작할 때 유용하다. 아웃바운드 포트 소진 문제에는 도움이 되지 않는다.

연결 풀링
근본적인 해결책은 대개 아키텍처 수준에 있다. 연결을 닫는 대신 재사용함으로써 TIME_WAIT 자체를 줄인다.
(ex. http keep-alive, http/2 멀티플렉싱, 데이터베이스 연결 풀)

인바운드 연결을 받는 서버라면 TIME_WAIT이 문제될 일이 거의 없다. 클라마다 다른 소스 포트를 쓰기 때문에 충돌이 생기지 않는다.
서버의 리스닝 포트는 TIME_WAIT에 진입하지 않는다.

같은 목적지로 빠르게 아웃바운드 연결을 만드는 클라나 프록시라면 TIME_WAIT이 포트를 소진시킬 수 있다.
tcp_tw_reuse를 활성화하거나 연결 풀링을 도입하거나 또는 둘 다 적용한다.
