# TCP

## 4Way Handshake
<img width="545" height="472" alt="image" src="https://github.com/user-attachments/assets/4295f933-b641-4c83-8b92-7aaf2d6279ee" /><br/>
a(active closer), p(passive closer)<br/>
a 상태 변화: established -> FIN_WAIT1 -> FIN_WAIT2 -> TIME_WAIT -> CLOSED<br/>
p 상태 변화: established -> CLOSE_WAIT -> LAST_ACK -> CLOSED<br/>

1. a는 FIN을 보내고 FIN_WAIT_1 상태가 되어 상대의 ACK를 기다린다.
2. p는 FIN을 받고 ACK 응답 후 CLOSE_WAIT 상태가 된다.
3. a는 ACK 응답을 받으면 FIN_WAIT_2 상태가 되어 상대의 FIN을 기다린다.
4. p는 FIN을 보내고 상태가 LAST_ACK가 된다.
5. a는 FIN를 받고 ACK를 응답한 뒤 TIME_WAIT 상태가 된다.
6. p는 상대의 ACK를 받고 CLOSED.
7. a도 timewait 대기 후 CLOSED.

### 애플리케이션 레벨 포함
a에서 close() 호출하여 상대에게 FIN 전송 후 FIN_WAIT_1 상태로 변경, 타이머가 있어서 상대에게 ACK를 듣지 못하더라도 문제가 없다.<br/>
timeout -> RST 전송, CLOSED<br/>
ACK 수신 -> FIN_WAIT_2<br/>

p의 커널에서 상대의 FIN을 수신 후 ACK 응답 후 CLOSE_WAIT 상태로 변경 후 수신 버퍼에 EOF를 넣는다.
CLOSE_WAIT 상태라는 것은 상대의 종료를 확인 후 애플리케이션 레벨에서 종료를 위한 준비를 기다려주는 것으로
"애플리케이션 recv() -> EOF로 상대 종료 확인 -> 데이터 정리 등 종료 준비 -> close 호출 -> FIN 전송" 수순으로 동작한다.
FIN 전송 후 p는 LAST_ACK 상태로 진입한다.<br/>

### 주의
CLOSE_WAIT 상태는 애플리케이션에서 close를 호출하기 전까지 커널에서 기다려주겠다는 것으로 내부 타이머가 존재하지 않는다.
1) p에서 상대방 FIN 수신 후 애플리케이션에서 close를 호출 X (행 등)
2) a에서 상대방에서 RST 조차도 보내지 못 할 경우(선뽑, 정전 등)

위의 두 조건이 만족하면 CLOSE_WAIT은 프로그램을 종료하거나 close를 호출할 때까지 CLOSE_WAIT으로 유지하게 된다.

SO_LINGER<br/>
closesocket()을 호출했을 때 커널이 버퍼에 남은 데이터를 상대방에게 다 보낼 때까지 지정한 시간 동안 프로세스를 대기시켜 안전하게 전송 후 종료.<br/>




## TCP Keep Alive
TCP 연결은 신뢰할 수 있도록 설계되었지만 거기에도 맹점이 있다. 예를 들어 상대방이 FIN, RST 패킷을 보낼 수도 없게 종료될 때(전원 끊김, 케이블 끊김 등), 이쪽에서는
이를 인지 못하고 연결을 유지하게 된다. 이 상태로 파일 디스크립터, 메모리, 연결 풀을 낭비하게 된다.<br/>

TCP의 신뢰성 메커니즘은 ***확인 응답(ACK)*** 이다. 타임 아웃을 활용하여 상대방의 ACK를 받음으로써 신뢰성이 지켜지는 것으로 이는 ***데이터를 전송할 때만*** 동작한다.
데이터를 보내지 않고 ***유휴 상태인 경우 확인할 수 없다.*** <br/>

이를 해결하기 위해 ***Keep-Alive*** 를 사용한다. 애플리케이션에서 데이터가 흐르지 않을 때(유휴 상태) 운영체제에서 원격지로 작은 프로브 패킷을 던지고
원격지에서 응답을 하면 살아 있는 것, 응답이 없으면 연결이 끊긴 것으로 간주하여 연결을 끊는 방식으로 구체적으로는 아래와 같이 동작한다. <br/>

### Keep-Alive 옵션
* Keep-Alive Time: 첫 번째 프로브가 나가는 타이머 (기본 7200초, 2시간)
* Keep-Alive Interval: 첫 번째 이후 프로브 간격 (기본 75초)
* Keep-Alive Probes: 연결 종료를 선언하기 위한 총 프로브 횟수 (기본 9번)

***(리눅스 기준)*** 애플리케이션의 마지막 데이터 송수신 후 타이머를 돌리고 시간이 다 될 동안 활동이 없으면 운영체제는 프로브 패킷을 전송한다(Keep-Alive Time).
이에 상대방이 응답하면 타이머 리셋, 응답이 없으면 다음 프로브 패킷이 전송된다(Keep-Alive Interval). 이 후로 몇 번 더 실패하면 해당 연결은 
끊긴 것으로 간주하고 끊는다(Keep-Alive Probes). <br/>

Keep-Alive 옵션을 사용하려면 ***소켓에서 Keep-Alive를 활성화하고 위의 세 변수를 조정하여 사용한다.*** 리눅스에서 기본값으로 잡혀 있는 수치가 너무
보수적이기에 사용하려면 ***위의 옵션값에서 수치를 조정해서 사용해야 한다.*** <br/>

부연 설명으로, 프로브 패킷은 일종의 트릭으로, 의도적으로 잘못된 시퀀스 번호를 전송하여 상대방의 수정 응답을 유도하는 것으로 이 패킷을 보내서
상대방에게 "나는 x번째 바이트를 기다리고 있어"라는 응답을 강요하는 것.<br/>

***Keep-Alive도 한계점***이 존재한다. Keep-Alive는 애플리케이션간에 대화가 없을 때 운영체제간에 tcp로 확인하는 것으로, ***커널 레벨의 확인***이라는 것.
예를 들어 애플리케이션이 교착 상태에 빠져 동작할 수 없는 상태에서도 운영체제에 의해 TCP 프로브 패킷에 응답할 수 있다. ***애플리케이션 수준의 장애를 감지하려면
애플리케이션 수준의 허트비트가 필요하다.*** <br/>

프로브 패킷은 페이로드없이 헤더만 있기는 하지만 이 또한 대역폭을 소비한다. 현대 네트워크에서는 거의 문제가 되지 않지만 제한된 환경에서는 고려할 가치가 있다고 하며
모바일 장치에서 잦은 프로브 패킷은 네트워크 인터페이스가 절전 모드로 들어가는 것을 막는다고 하며 모바일 애플리케이션은 keep-alive를 사용하지 않거나 빈도를 크게 줄인다고 한다.

## 네이글 알고리즘, TCP_NODELAY
TCP로 데이터를 송수신할 때 무조건 오버헤드가 따른다. ip 헤더(20)+tcp 헤더(20)+이더넷 프레임(18)+보내고자 하는 데이터(a). 
애플리케이션이 단 1바이트를 전송하면 그 1바이트는 59바이트 패킷에 담겨 이동한다.
```
오버헤드:  핵심 목적을 달성하기 위해 부가적으로 들어가는 비용
```
총 59바이트 전송에서 핵심 목적 1바이트, 그를 위해 추가되는 바이트(오버헤드)가 58바이트로 이를 비율로 나타내면 58/59 => 대략 98%가 오버헤드다.<br/>
이렇게 tcp는 데이터를 전송할 때 무조건 오버헤드가 있으며, 보내고자 하는 데이터의 크기가 작을수록 오버헤드가 늘어나기에,
네이글 알고리즘은 이 오버헤드를 최대한 줄이기 위해 패킷을 모아서 보내는 것.<br/>

네이글 알고리즘 설정은 소켓에서 TCP_NODELAY 옵션으로 설정하는데, 활성화하면 네이글 알고리즘을 사용하지 않겠다는 것으로, 패킷은 더 많아지고 오버헤드도 늘어나지만
즉각적인 전달이 보장된다.<br/>

### 네이글 알고리즘 규칙
* 전송할 데이터가 MSS(최대 세그먼트 크기, Maximum Segment Size) 이상이라면 즉시 전송.
* 전송할 데이터가 MSS 미만인데 이전에 보낸 데이터가 없으면(ACK를 못 받은 게 없으면) 즉시 전송.
* 전송할 데이터가 MSS 미만인데 이전에 보낸 데이터가 있으면(ACK를 못 받은 게 있으면) 꽉 찰 때까지 대기.
첫 번째 전송은 즉시 전송, 그 후의 전송들은 MSS를 채우면 즉시 전송, 그렇지 않으면 기존에 보낸 패킷들에 대한 ACK를 받을 때까지 대기.<br/>

이 방식은 네트워크 상황에 맞게 스스로 조절된다. ACK가 빠른 네트워크에서는 버퍼링이 최소화된다.
ACK가 지연되는 느린 네트워크에서는 더 적극적인 일괄 처리가 일어난다. 

### 사용 사례
실시간 게임의 경우 플레이어의 입력은 서버에 바로 도달해야 한다.

실시간 게임이 전형적인 사례이다. 플레이어의 입력은 서버에 바로 도달해야 한다. 왕복 지연을 기다릴 여유가 없다. 플레이어는 30~50ms 이상의
지연을 체감한다. 다음 입력을 보내기 전에 ACK를 기다리면 게임이 느리고 반응 없는 것처럼 느껴진다.<br/>

원격 데스크톱 프로토콜은 마우스 위치를 즉시 업데이트해야 한다. 일괄 처리 지연이 발생하면 커서가 사용자의 손 움직임보다
뒤쳐지게 되고 이 괴리감이 사용자를 불편하게 한다.<br/>

대용량 데이터 전송(파일 다운로드, 백업, 동기화)은 네이글 알고리즘을 유지해야 한다. 메가바이트 단위로 데이터를 이동할 때는
꽉 찬 패킷이 중요하고 지연은 문제가 되지 않는다.

### 지연된 ACK 문제 (delayed ACK) - 이부분 정리 필요
tcp의 효율 설정인 delayed ack와 상성이 좋지 않다.
<br/>
수신측은 모든 패킷에 즉시 ACK를 보내지 않는다. 발신 데이터에 ACK를 편승시키거나 여러 패킷을 한꺼번에 확인
응답하기를 기대하며 최대 200ms까지 기다린다.

### 모두가 TCP_NODELAY를 사용하면 네트워크 혼잡이 생기지 않나?
TCP의 혼잡 제어는 네이글 알고리즘과 별개로 동작한다. ***TCP_NODELAY가 활성화되어 있어도***
TCP는 패킷 손실과 네트워크 피드백에 따라 전송 속도를 조절한다. ***혼잡이 감지되면 속도를 줄인다.***

### 일부는 좀 기다렸다가 보낼 수 없나?
TCP NODELAY 설정했다고 패킷을 쏠 때마다 보내는 게 아니라 어떤 건 좀 모았다가 보내게 할 수 없나? 애플리케이션 계층에서 직접 처리해야 한다.

### UDP에서는?
UDP는 확인 응답이나 연결 상태의 개념이 없으므로 네이글 알고리즘이 적용되지 않는다. UDP의 모든 전송은 즉시 패킷이 된다.
UDP 애플리케이션에서 일괄 처리가 필요하다면 직접 구현해야 한다.

### 결론, 정리
네이글 알고리즘은 지연과 네트워크 대역폭 사이에서 트레이드 오프를 결정하는 것으로 지연에 민감하다면 TCP_NODELAY를 활성화해야 한다.
TCP_NODELAY의 활성화, 비활성화의 동작 방식이 너무 극단적이라고 생각된다면 TCP_NODELAY를 활성화한 후 애플리케이션 레벨에서
조절하는 것을 직접 구현해야 한다.


## TIME_WAIT
tcp에서 연결을 먼저 종료하는 측에서 연결을 종료 후 일정 시간 대기하게 되는 상태로 소켓은 커널의 연결 테이블에 남아 "로컬 주소, 로컬 포트, 원격 주소, 원격 포트"의
정확한 조합이 즉시 재사용되지 않도록 막는다. 지속 시간은 2MSL(MSL, Maximum Segment Lifetime, 최대 세그먼트 수명)로
최대 세그먼트 수명의 2배이다. MSL은 TCP 세그먼트가 네트워크에서 폐기되기 전까지 살아있는 이론적 최대 시간으로 보통 30초이다.<br/>

### TIME_WAIT이 존재하는 이유는 아래 2가지 때문이다.
#### 떠도는 패킷 문제
이전 연결에서 출발한 패킷이 새로 연결이 성립된 뒤에 도착하고 유효한 데이터로 받아들여 질 수 있다.
#### 손실된 ACK 문제
정상 종료를 위해 최악을 가정해 기다리는 것으로 4way handshake의 가장 마지막에 a가 보내는 ACK가 유실되면 p는 FIN을 재전송하게 된다.
a에서 재전송된 FIN 수신을 하지만 TIME_WAIT이 끝나 RST로 응답, p에서는 RST에 의한 강제 종료.<br/>

그러니까 TIME_WAIT은 a가 내가 이 통신의 마지막을 책임지고 정리하겠다.

## UDP - 정리 필요
tcp는 신뢰성 있는 통신을 위해 ACK, 재전송, 순서 보장 등 갖은 수단을 동원. 하지만 서비스에 따라 늦게 도착한 패킷이 아예 도착하지 않은 패킷보다 더
나쁠 수 있다. 이럴 때 TCP는 원하지도 않는 그 패킷을 굳이 재전송해주고 기다리게 만든다. 전송을 보장하기 위해 설계된 프로토콜이 오히려
서비스를 방해할 수 있다.<br/>

### 실시간 통신
음성 통화에서 대화 중 20ms 분량의 오디오가 담긴 패킷이 손실되어도 거의 알아차리기 힘들다. 하지만 TCP가 재전송을 고집하는 바람에
해당 패킷이 200ms 늦게 도착한다면, 어색한 지연이 생기고 사람들의 말이 겹치게 된다. UDP는 애플리케이션의 자체적인 복구 전략을 구현할 수 있게 해준다.
최신 오디오 코덱은 손실된 샘플을 보간하고, 비디오 코덱은 손상된 프레임을 건너뛴다. 결과적으로 완벽함보다 타이밍이 더 중요한 자연스러운 대화가 가능해진다.
Zoom, Discord, WebRTC 모두 미디어 스트림에는 UDP를 사용하고 TCP는 채팅과 제어 신호에만 사용한다.

### 게임
온라인 게임은 가능한 가장 낮은 지연 시간을 요구한다. fps에서 점프 버튼을 누르면 그 동작은 수십 ms 안에 서버에 도달하고 모든 플레이어에게 반영되어야 한다.
tcp의 재전송 지연은 빠른 템포의 게임을 느리게 느껴지게 만든다.

UDP를 사용하는 게임 개발자들은 선택적 신뢰성을 구현한다. 플레이어 위치 업데이트에는 UDP를 사용하고 손실되더라도 16ms 후 다음 업데이트에서 이를 수정한다.
플레이어가 무기를 발사했다에는 수신 확인과 잠재적 재전송이 필요하다. 이런 게임은 획일적인 tcp 대신 게임 방식에 맞게 애플리케이션 계층에서 직접 구현한다.
위치 업데이트는 신뢰성 보다는 빈도를, 아이템 변경은 신뢰성을 우선한다.

### 라이브 스트리밍
주문형 비디오(VOD)는 버퍼링할 수 있다. 라이브 스트리밍은 그럴 수 없다.

### DNS와 요청-응답 프로토콜
DNS는 단순한 교환에서 UDP의 효율성을 잘 보여주는 예이다. pc에서 "www.naver.com"을 조회할 때 UDP 패킷 하나를 보내고 패킷 하나를 돌려받기를 기대한다.
TCP는 연결을 수립하는 데만 패킷 3개가 필요하다. 그 다음 쿼리와 응답, 그리고 연결 해제의 수순을 거쳐야 한다. 단순한 질문과 답에 오버헤드가 몇 배로 늘어난다.
DNS는 UDP를 사용하고 자체적인 재시도 로직을 구현한다. 몇 초안에 응답이 없으면?  쿼리를 다시 보낸다. NTP(시간 동기화), SNMP(장비 모니터링), DHCP(네트워크 구성)도
동일한 패턴을 따른다.

### 추가
UDP는 패킷이 전송된 순서와 다르게 도착하거나 아예 도착하지 않을 수 있다. UDP를 사용하는 앱은 이를 처리해야 한다.
UDP가 TCP보다 더 빠른 것은 아니다. 더 단순할 뿐이며 책임을 애플리케이션으로 이전한다. 대부분의 앱(웹 브라우징, 파일 다운로드, 이메일 등)에서는
TCP의 보장이 필요한 것이며 신뢰성을 재구현하는 것은 낭비이다.

### 그래서 정리하면
* 완전함보다 타이밍이 중요: 실시간 통신, 게임, 라이브 스트리밍
* 교환이 단순할 때:DNS, NTP, DHCP
* 맞춤형 신뢰성이 필요할 때
* 일대다 통신이 필요할 때: 멀티캐스트
애플리케이션이 지연보다 패킷 손실을 더 잘 처리할 수 있다면 UDP를 선택하는 것이 좋다.

## UDP 동작
UDP는 상태, 연결이란 것이 없고 그렇기에 연결 수립, 연결 종료도 없다. 데이터 전송이 필요하면 데이터그램을 만들어 전송한다.
각 데이터그램은 완전히 독립적으로 다른 데이터그램과는 관계없다. 송신측에서 목적지 ip 주소와 포트 번호로 지정하고 ip 계층에 넘기는 순간
UDP의 역할은 끝이난다. 그 다음 전송한 이 데이터그램이 도착하는지, 손실되는지, 순서가 바뀌든지는 UDP가 신경 쓸 일이 아니다.
<br/>
단점이 큰 것 같지만 이러한 방식은 패킷 시퀀스 번호를 체크할 필요가 없고 대역폭을 소비하는 확인 응답 패킷도 없고 응답을 기다리는 타이머도 없다.
이러한 이유로 더 빠른 프로토콜이 된다.

### 최소한의 헤더
UDP넌 3개의 필드로 구성된 단 8바이트의 헤더를 사용하고 여기서 UDP의 철학이 잘 드러난다.
출발지 포트(16비트)
목적지 포트(16비트)
길이(16비트): 헤더를 포함한 데이터그램의 전체 크기, 이론상 최대 크기는 65535바이트지만 네트워크 제약으로 인해 실제 한도는 더 작다.
체크섬(16비트): 전송 중 비트가 손상되었는지 감지한다. 이에 대한 처리를 애플리케이션에서 결정한다.(재전송 or 폐기)

UDP는 신뢰성 메커니즘을 제공하지 않는다.
데이터 그램이 손실나도 신경쓰지 않는다.
UDP는 순서를 보장하지 않는다.
UDP는 흐름 제어가 없다. 수신자가 처리에 벅차하더라도 속도를 늦추지 않는다. 수신 속도보다 전송이 더 빠르면 초과되는 패킷은 그냥 버린다..
UDP는 혼잡 제어가 없다. 네트워크 혼잡을 감지하거나 전송 속도를 조정하지 않는다.

* Keep-Alive
  * TCP 원격지 생존 확인용
  * Keep-Alive는 커널 레벨 확인법으로 애플리케이션 레벨 체크 불가, 애플리케이션 수준 허트비트 구현 필요.
  * 둘 다 사용하는 방법도 있지만 현재로는 애플리케이션 레벨에서만 구현하는 것이 좋아보임

* Nagle 알고리즘, TCP_NODELAY
  * "네트워크 대역폭을 아낄래(모아 보내기), 지연을 줄일래(바로 보내기)"에서 선택하는 것.
  * 게임 서버의 경우 지연을 선택해야 한다.
  * 다만 지연을 선택하고 애플리케이션 레벨에서 이를 조절하는 식으로 구현 필요.

  * TCP 연결 종료 과정.
