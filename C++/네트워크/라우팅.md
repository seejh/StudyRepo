# 라우팅
경로 결정

## 라우팅 방식
정적 라우팅, 동적 라우팅<br/>
* 정적 라우팅: 관리자가 직접 경로 입력
* 동적 라우팅: 라우터 간의 정보 교환으로 라우터가 경로 결정


### 아래와 같이 네트워크가 구성되어 있다고 하자
<img width="800" height="450" alt="image" src="https://github.com/user-attachments/assets/8eef3b03-a934-4495-933f-43ff1b0315ee" /><br/>
라우터에 직접 연결된 경로는 라우팅을 수행하지 않아도 라우팅 테이블에 기본적으로 등록되며 코드가 C로 올라온다.<br/>
그러나 이 상태에서 송신지(10.0)에서 수신지(20.0)로 데이터를 보낼 수는 없다.<br/>
라우터는 데이터가 들어왔을 때 패킷의 3계층 헤더에 들어간 목적지 ip 주소를 자신의 라우팅 테이블에서 찾는다.<br/>
없다면 패킷을 폐기하게 되며 통신을 할 수 있게 만들기 위해 필요한 것이 라우팅이다.<br/><br/><br/>

192.168.20.0, 192.168.10.0 대역을 관리자가 직접 입력하면 정적 라우팅.<br/>
라우팅 프로토콜을 통해 라우터간에 정보를 교환하고 교환된 정보를 바탕으로 라우터가 최적 경로를 계산, 결정하면 동적 라우팅.<br/>

## OSPF (Open Shortest Path First)
동적 라우팅, 가장 많이 사용, 국제 표준 라우팅 프로토콜(어느 장비에서도 사용 가능)<br/>
링크 상태 정보를 교환하는 링크 상태 라우팅 프로토콜<br/>

* LSA (링크 상태 정보, 원래는 Link State Advertisement)
  * ip 주소, 서브넷 마스크, 연결된 네트워크 종류 등 링크의 모든 상태 정보
  * 링크: 라우터에 연결된 인터페이스로 R2의 경우 fa0/1, se0/1이고 R1의 경우 fa0/0, se0/0이 LSA로 날라간다.
  * =라우터에 연결된 인터페이스 정보 교환

OSPF는 30분마다 주기적인 업데이트, 토폴로지 변경이 발생하면 즉시 업데이트<br/>
OSPF는 3가지 테이블을 가진다.<br/>
* Neighbor 테이블
  * Hello 패킷을 교환해 인식된 라우터의 정보가 등록되는 테이블
* LSDB 테이블
  * OSPF에서 교환된 모든 링크 상태 정보가 등록되는 테이블
* Routing 테이블
  * 모든 링크 상태를 가지고 있는 LSDB 테이블에서 SPF 알고리즘을 통해 결정된 최적의 경로가 등록되는 테이블

## OSPF 동작
1. OSPF 네이버 관계<br/>
<img width="800" height="450" alt="image" src="https://github.com/user-attachments/assets/a40437e9-dc10-40c3-ab7b-03ee670aaf56" /><br/>
OSPF가 동작하는 라우터를 인식하기 위해 Hello 패킷을 교환하게 된다.<br/>
Hello 패킷을 교환 후 네이버가 되고 이를 네이버 관계라고 한다.<br/>
관계를 맺은 후에도 이 관계를 유지하기 위해서 10초마다 Hello 패킷을 보낸다.<br/>

* Hello 패킷 구성
  * (1) 라우터 ID
  * (2) 헬로 간격과 데드 간격
    * 헬로 패킷을 보내는 간격 기본 10초
    * 헬로 패킷을 받지 못해도 네이버 관계를 유지해주는 시간 기본 40초
  * (3) 영역 ID
    * 하나의 링크로 연결된 두 라우터의 인터페이스는 동일한 영역(Area)에 속해야 한다.
  * (4) 라우터 우선순위
  * (5) DR ID, BDR ID
  * (6) 인증 암호
    * 허가되지 않은 라우터와 네이버 관계를 형성하는 것을 막는법
    * 허가되지 않은 라우터와 네이버가 된다면 우리 라우터의 정보를 허가 받지 않은 대상에게 보내주게 된다.
    * 인증 방법으로는 무인증(인증을 하지 않는다), 평문 암호(그냥 텍스트), MD5가 있다
  * (7) SA 플래그
    * OSPF 멀티 영역에서 사용하는 특수 영역, 현재는 단일만 학습했기 떄문에...
  * 이 중에서 2, 3, 6, 7은 서로 보내는 내용이 동일해야 네이버 관계를 맺을 수 있다.

<br/>
2. 링크 상태 정보를 교환하는 과정<br/>
<img width="800" height="450" alt="image" src="https://github.com/user-attachments/assets/93b70d2f-90d1-4e60-b94b-1ef52d94dd79" /><br/>
현재 R1과 R2는 네이버 관계이다.(헬로 패킷 교환 직후)<br/>
현재 R1, R2 라우터의 LSDB 테이블을 보면 직접 연결된 링크 정보만 있는 상태이다.<br/>
<img width="800" height="450" alt="image" src="https://github.com/user-attachments/assets/e947f8a3-c409-46be-82c4-486ac32dd7ad" /><br/>
R1에서 본인의 링크 상태 정보의 요약을 담은 DBD 패킷을 R2에게 보낸다.<br/>
R2에서는 R1의 링크 상태 정보와 비교하여 본인에게 없는 링크 상태 정보를 요청하게 된다.(LSR)<br/>
R1에서는 LSR 패킷을 받고 LSU 패킷으로 링크 상태 정보를 보내준다.<br/>
R2에서는 LSU 패킷을 받고 본인의 LSDB 테이블에 해당 링크 상태 정보를 저장한다.<br/>
현재는 R1 기준으로, R2에서도 이 과정을 거친다.<br/>
이 과정을 거쳐서 양쪽의 LSDB 테이블이 같아지는 것을 LSDB 동기화라고 하며 동기화가 되면 링크 상태 교환이 완료된다.<br/>

라우팅 설정법(OSPF)

router ospf 프로세스ID
OSPF를 사용하겠다.
프로세스ID
라우팅 프로세스를 식별하기 위한 값
라우터에서 여러 ospf를 사용할 수 있는데 그걸 식별하기 위한 값
다른 ospf 라우터와 프로세스id가 일치할 필요는 없다.

network 인터페이스ip주소 0.0.0.0(와일드카드마스크) area 영역ID

광고는 어디로 알려줄건지

R2
enable
